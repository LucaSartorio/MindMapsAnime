# AniMapVerse 3D Explorer

Procedural, optional 3D exploration of narrative locations. Rules (what must stay true): `.claude/rules/explorer-3d.md`.
Procedure to add a location: `/create-3d-location` (`.claude/skills/create-3d-location/SKILL.md`). This document
explains how it works and why, so a future session can add a scene without re-analysing the architecture.

## 1. Principles

- **Optional extension, zero cost for everyone else.** Nothing 3D is downloaded, parsed or executed until a user
  clicks "Explore in 3D". No new route, no prerendered page, no backend, no server GPU, no extra service.
- **Everything is code.** Locations are generated by TypeScript (parametric primitives, seeded randomness, canvas or
  data textures). No glTF/FBX/OBJ, no Blender, no downloaded or traced artwork, no AI-generated meshes. Why: no asset
  pipeline or licence chain to manage, deterministic output (same code → same scene), tiny downloads (the whole
  Baratie is ~14 KB gzip of code), and every element can be tagged canon or interpretive in data.
- **Plain Three.js, no React Three Fiber/Drei.** Decision taken in this repo (React 18): R3F 8 supports React 18 but
  adds a reconciler and per-frame React work we do not need; scenes are imperative builders baked into few merged
  meshes; the lifecycle (render on demand, explicit `dispose`, forced context loss) is easier to guarantee by hand.
  OrbitControls comes from `three/addons`. Revisit only if scenes need declarative composition.
- **Dataset-driven and world-agnostic.** The engine never names a world. A scene is data (`config.ts`) + a builder
  (`scene.ts`) + one registry entry; hotspots point at existing dataset ids, labels come from the dataset.

## 2. Structure (`src/features/explorer3d/`)

| Path | Bundle | Responsibility |
|---|---|---|
| `types.ts` | types only | contract: manifest, scene definition (zones, spawns, hotspots, provenance), quality |
| `launcher/manifests.ts` | ordinary (WorldRoute chunk) | which location has a scene, `prototype` / `available` |
| `launcher/loaders.ts` | ordinary | the only `import()` of scenes; prototype loaders wrapped in `__EXPLORER_3D_PROTOTYPES__` |
| `launcher/registry.ts`, `store.ts` | ordinary | lookups, WebGL probe (on click), viewer session state (zustand) |
| `launcher/Explorer3DButton.tsx` | ordinary | "Explore in 3D" in `LocationDetailsModal` footer (renders nothing without a scene) |
| `launcher/Explorer3DHost.tsx` | ordinary | mounted in `ModalRoot`; lazy viewer + Suspense + error boundary; closes on route change |
| `viewer/` | lazy 3D chunk | full-screen dialog UI, hotspot list, quality select, joystick |
| `engine/` | lazy 3D chunk | `SceneRenderer`, `ExplorerSession`, collisions, controls, hotspots, quality, resources, batching |
| `primitives/` | lazy 3D chunk | parametric architecture, ships/lofts, furniture (instancing), ocean/sky/clouds/lights |
| `materials/toon.ts` | lazy 3D chunk | cel-shaded kit: vertex-coloured toon, glow, ink lines, inverted-hull outline |
| `worlds/<world>/<location>/` | lazy scene chunk | `config.ts` (data, three-free) + `scene.ts` (builder) |

Build tooling: `scripts/vite/explorer3dGuard.ts` (Rollup plugin), `scripts/validate-3d.ts`, `scripts/test-3d*.ts`,
`scripts/explorer3d-{lab.ts,bundle-report.mjs}`. Scene ledgers: `docs/explorer3d/<scene-id>.md`.

## 3. Loading path and isolation

```
LocationDetailsModal ─ Explorer3DButton (click) ─▶ canUseWebGL()? ─no─▶ inline message, nothing downloaded
                                     │ yes
                                     ▼
Explorer3DHost ── import('viewer/Explorer3DViewer') ──▶ [viewer chunk] + [three chunk]
                                     │
Explorer3DViewer ── SCENE_LOADERS[id]() ── import('worlds/…/scene') ──▶ [scene chunk]
```

Three independent gates keep this true:
1. `npm run validate:3d` (sources, TypeScript AST): outside the explorer only `launcher/` and `types.ts` are
   imported, nothing imports `three`, dynamic entry only from `launcher/`.
2. Build guard (every `vite build`, so Site CI): on Rollup's real chunk graph, no chunk containing three.js or
   explorer code is statically reachable from the entry or from any ordinary lazy route (which is also what the
   prerender modulepreloads). It fails the build otherwise, and lists the 3D chunks in
   `node_modules/.cache/animapverse/explorer3d-report.json` (outside `dist/`).
3. `npm run test:3d` and `npm run smoke`: real Chromium requests on ordinary pages contain no 3D chunk.

**Feature flag.** `vite.config.ts` defines `__EXPLORER_3D_PROTOTYPES__` = `npm run dev` or `VITE_EXPLORER_3D=1`.
Production builds leave it false: a prototype loader becomes `undefined` and Rollup does not even emit its scene
chunk. The flag is never switched on for production: scenes become public one by one. Prototypes can be tested
locally (`npm run dev`) or on a preview built with `VITE_EXPLORER_3D=1`. Making a scene public = manifest status
`available` + an ungated loader + `provenance.rights` `'cleared'` (rights verified) or `'owner-approved'` (owner
decision recorded in `provenance.publication` with its open questions) — `validate:3d` enforces all three (§10).

**Public scenes (production):** `onepiece-baratie` since 2026-11-27 (owner-approved, rights not verified). Its scene
chunk, the viewer and three.js are emitted in `dist/` and downloaded only after the click; ordinary pages still
request none of them (build guard, smoke, `test:3d`).

**SSR.** Server and first client render are identical: the button depends only on build-time data; the host renders
nothing while closed; WebGL, `window` and `document` are touched only in click handlers and effects. The SSR build
never executes the viewer (three stays an external of `dist-server/` and is never imported).

## 4. Scene lifecycle

1. Click → `performance.mark('explorer3d:open')`, WebGL probe, viewer chunk download, location scheda closes.
2. Viewer mounts → scene chunk download → `new ExplorerSession(host, module, opts)`:
   `SceneRenderer` (one `WebGLRenderer`, canvas, ResizeObserver, visibility, context-loss listeners) →
   initial quality (`initialAutoLevel`) → `module.build(ctx)` with a fresh `ResourceTracker` and material kit →
   colliders → hotspots → orbit + walk controllers → first frame.
3. Interaction: on-demand rendering (`requestRender` / `setContinuous`). Orbit inertia ends once camera motion is
   invisible; walking renders only while keys/joystick/fall are active; hidden tab → loop stopped.
4. Zone loading: `SceneBuild.interiors` groups are built the first time the player walks within 8 m of one of their
   zones (never in observation mode). `SceneBuild.details` are hidden beyond `detailDistance`.
5. Manual quality change → the scene is rebuilt at that level in the same WebGL context (old tracker disposed);
   auto changes only toggle runtime parameters (DPR, shadows, outlines, fog, detail distance).
6. Close / route change / "open the entry" → `session.dispose()`: controllers and listeners removed, tracker frees
   every geometry, material, texture and shadow map, `renderer.dispose()` + `forceContextLoss()`, canvas removed,
   debug handle deleted. The location scheda (or the chosen entity's scheda) reopens.

## 5. Memory and GPU resources

- Ownership: everything created for a session goes through `ctx.tracker.track()`. Objects shared inside the session
  (unit box/cylinder/sphere geometries, the material kit, marker textures) are tracked once, so they are freed
  exactly once and never while in use. Nothing is cached across sessions: re-opening rebuilds from code (~35 ms),
  which makes leaks measurable.
- Batching: `GeometryBatch` bakes hundreds of parts (already transformed, vertex-coloured) into one non-indexed
  geometry → one draw call per batch. Repeated furniture uses `InstancedMesh`. Ink lines reuse the batch geometry.
- Verified by `test:3d`: 10 open/close cycles → 0 live WebGL contexts, identical window/document listener sets,
  identical `renderer.info.memory` counts per session, heap +0.8 MB (measured with `--expose-gc`).
  `renderer.info` reports object counts, not GPU bytes.

## 6. Quality presets (`engine/quality.ts`)

| | low | medium | high |
|---|---|---|---|
| DPR cap | 0.75–1 | 1–1.25 | 1–1.5 |
| Shadows | off | 1024² | 2048² |
| Outlines (ink) | off | on | on |
| Ocean grid / waves | 1 quad, flat | 64², waves | 128², waves |
| Curve segments | ×0.5 | ×1 | ×1 |
| Detail distance / fog | 45 / 260 m | 90 / 420 m | 180 / 600 m |
| Target frame time | 33 ms | 22 ms | 16.7 ms |

`auto`: initial level from device hints (cores, `deviceMemory`, coarse pointer, pixels to shade, max texture size,
software rasterizer → low) — never the user agent; then `AutoQualityController`: 90th-percentile frame time over
2 s windows of continuous frames; down after 2 slow windows (> 1.25× target), up after 4 fast windows (< 0.6× the
next level's target), 3 s cooldown, and a level abandoned for slowness is never re-entered (no ping-pong). Still too
slow at `low` → a notice suggests leaving. The choice is remembered in `localStorage` (try/catch, per viewer).
`prefers-reduced-motion`: no orbit inertia, no water animation.

## 8. Adding a location (summary of `/create-3d-location`)

1. Check the location and its links in the dataset (hotspots may only use them). 2. Collect references (§8.1),
decide canon vs interpretive, open `docs/explorer3d/<scene-id>.md` from the template. 3. Write
`worlds/<world>/<location>/config.ts` (plan constants + `export const definition`) and `scene.ts`
(`export const scene`). 4. Register in `launcher/manifests.ts` (`status: 'prototype'`) and `launcher/loaders.ts`
(flag-gated `import()`). 5. `npm run validate:3d && npm run test:3d:unit && npx tsc -b`, visual iterations with
`npm run capture:3d` in `npm run dev`, `npm run test:3d`, `npm run benchmark:3d`, `npm run smoke`. No engine change
is needed unless the scene needs a new capability (then: world-agnostic, documented here).

### 8.1 Reference-driven modelling and fidelity iterations

Text alone gives the parts of a place, not its look: the Baratie's first version (text-only) had the right parts
with wrong colours, masses and silhouette. The method (`/create-3d-location … fidelity`, and §2/§5 of the skill for
new scenes):
- **References**: original anime first, then manga, then official merchandise (model kits: stylized, compressed
  proportions — read shapes/colours/layout, not dimensions), owner-provided images. Only legitimately accessible
  sources; blocked pages (paywall, anti-bot) are dropped, never worked around. Images are looked at in the
  scratchpad only: never committed, embedded, traced or sampled into textures. Each is listed in the scene ledger.
- **Captures**: `npm run capture:3d -- <scene-id> --out <dir> [--quality low|medium|high] [--compare <before-dir>]`
  renders fixed views (hero, bow, side, rear, top, sea from the scene camera; one walking view per spawn) with the UI
  hidden; `--compare-only <before> <after>` builds a before/after sheet (`compare.html` + `compare.png`).
- **Loop**: differences ranked silhouette/proportions → palette → details; one round of changes; same views again;
  keep only visible, regression-free improvements; probe oddities with a raycast before editing; log every round.
  No similarity percentages, no claims about images that could not be opened.

### Reusable components

- `PartBuilder` (`primitives/parts.ts`): unit box, cylinder (optional arc), sphere, torus (optional arc), prism,
  square frustum + transforms into a batch. `GeometryBatch` colour functions receive position, normal and the source
  vertex colour (`SOURCE_COLORS`): two-tone walls (outside/inside from the normal), stripes, gradients for free.
- `segmentWall` (any plan segment; rectangular/arched windows, doors with fanlights, frames → colliders), `wall`
  (axis-aligned, portholes), `slab`, `stairs` (treads + ramp floor + side walls), `railing`, `latticeBand`
  (balustrades/friezes with X panels), `gableRoof`, `hipRoof`, plans (`ellipsePlan`, `chamferedPlan`, `openLoop`),
  `planFloors` (walkable slices of a convex plan, with stairwell holes), `segmentColliders`
  (`primitives/architecture.ts`).
- `loftGeometry`, `hullRings`, `deckOutline`, `deckFloorSlices`, `flatPolygon`, `flatShape` (plans with holes, up or
  down), `ellipsoidRings`, `extrudedSilhouette`, `sailGeometry` (billowed, double-sided, patterned)
  (`primitives/ships.ts`): hulls, decks, ring terraces, ceilings, organic heads, fins, tails, sails.
- `chairGeometry`, `roundTableGeometry`, `instanced`, `chairsAround` (`primitives/furniture.ts`).
- `createOcean` (toon bands, foam rings around a footprint, optional waves), `createSky`, `createClouds`,
  `createDaylight` (`primitives/environment.ts`).
- Zones (`engine/zones.ts`): interior zones win over the exterior that contains them; `footprint: 'ellipse'` for
  oval rooms.
- Engine: `CollisionWorld` (AABB walls + flat/ramp floors, step up/snap down, no walking off floors),
  `OrbitCameraController`, `WalkController` (WASD, pointer lock on explicit click, drag look, joystick),
  `HotspotLayer` (screen-sized markers, shape + colour per entity type).

### Hotspots

`{ id, entity: { type, id }, position, zone }`. Types: character, event, arc, place, faction (the existing schede).
`validate:3d` requires the entity to exist, to be linked to the location in the dataset and not to be
`needs_verification`. Selecting a hotspot (3D marker or the accessible list) shows its dataset name; "Open the entry"
closes the viewer and opens the scheda through `useOpenEntityRef`. Interior hotspots switch to exploration and
teleport to the zone's spawn.

## 9. Scalability (10 → 1,000 locations)

- Per scene: one lazy chunk (Baratie: 37.7 KB raw / 14 KB gzip, ~38 KB of source) + ~0.1 KB in the ordinary
  WorldRoute chunk (manifest + loader entry). Deploy and repository grow linearly; nothing is downloaded until used.
- 10 scenes: ~1 KB of launcher metadata; 100: ~10 KB raw (~3 KB gzip) — acceptable; beyond ~100, split
  `manifests.ts`/`loaders.ts` per world and load them with the world dataset chunk (they are keyed by `worldId`).
- 500–1,000 scenes: ~20–40 MB of emitted scene chunks in the deploy (static, CDN-cached, immutable) and ~20–40 MB of
  source; build time grows with Rollup work per chunk (measure with `benchmark:3d:bundle` and the build log before
  committing to that scale). The engine chunk stays shared and cached across scenes.
- Runtime: one scene at a time; client memory bounded by the active scene only.

## 10. Rights, provenance, limits

- The procedural reconstruction is original code, but a faithful representation of a protected location may still
  raise rights questions: every scene starts as `prototype` (not deployed to production), with
  `provenance.rights: 'pending-owner-review'`. Publishing needs the owner's explicit approval.
- Rights states: `pending-owner-review` (prototype only) · `owner-approved` (public by owner decision; rights NOT
  verified; `provenance.publication` = who, when, where recorded, unresolved questions, and `validate:3d` prints a
  warning on every build) · `cleared` (a verified clearance exists — never set it without one). A scene can move from
  `owner-approved` to `cleared` only when the open questions are actually resolved.
- Baratie: `owner-approved` on 2026-11-27. Open questions (also in `docs/explorer3d/onepiece-baratie.md`): no licence
  or permission from the rights holders requested or verified; no legal review of a recognizable 3D reconstruction
  under the site's fan-reference use; primary wiki description unreadable (proportions from secondary sources); the
  location name on the sign.
- `provenance` lists sources (textual references, chapters), author, licence and notes that separate canon from
  interpretive parts; zones carry `reconstruction`, shown in the UI as "Interpretive reconstruction".
- Known limits: no real-device FPS yet; collisions are AABB-based (curved hulls use slices/short boxes); auto quality
  does not rebuild geometry (only manual changes do); one shadow-casting light; no physics, NPCs or audio by design.
